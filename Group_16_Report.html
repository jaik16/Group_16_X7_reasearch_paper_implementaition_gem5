Abstract—
Modern high-performance out-of-order x86 processors deploy on-chip Micro-op (Uop) Caches between instruction fetch/decode and rename to bypass power-hungry, high-latency instruction length decoding and micro-op translation. While conventional CPU caches store fixed-size cache blocks (64 bytes) with uniform single-line hit utility, micro-op caches store Prediction Windows (PWs) characterized by variable micro-op costs and variable cache way storage footprints. Micro-op cache eviction deviates fundamentally from standard paging and maps directly to an online 0-1 Knapsack Problem. In this work, Group 16 presents a complete microarchitectural implementation and rigorous evaluation of the HPCA 2025 framework in the gem5 O3CPU modeling an AMD Zen 3-like frontend. Our framework implements dynamic Prediction Window accumulation, strict L1 instruction cache inclusiveness via hardware snooping, a 1-cycle switch delay penalty, and five replacement policies: LRU, SRRIP, Belady MIN offline trace replay, FLACK (cost-aware greedy unit-cost heuristic), and FURBYS (frequency and unit-cost replacement with 3-bit offline profile weights, 2-bit RRPV tie-breaking, selective bypass threshold K, and a 2-slot local miss-pitfall detection buffer with SRRIP fallback). Offline weights were clustered per set using Fisher-Jenks Natural Breaks optimization. Experimental evaluation confirms up to 67.5% window hit rate, delivering 50.8% of executed micro-ops directly from the uop cache, filtering 55.6% of L1 I-cache demand queries, and reducing frontend stall cycles.

I. Introduction & Background

A. The Instruction Frontend Bottleneck

Modern data center applications (web servers, databases, microservices, cloud RPCs) exhibit massive instruction footprints, deep call graphs, and frequent indirect branch mispredictions. In complex Instruction Set Architectures (ISAs) such as x86-64, instruction fetch and decode represents one of the primary performance and energy bottlenecks in the processor pipeline:

  • Variable-Length Instruction Decoding: x86 instructions vary from 1 to 15 bytes in length without fixed alignment boundaries, requiring multi-stage pre-decoders, instruction boundary markers, and parallel complex decoders that consume up to 20–30% of core dynamic power and impose 3–5 cycles of pipeline latency.
  • Macro-to-Micro-op Expansion: Single macro-instructions can expand into multiple micro-ops, creating pipeline bubbles whenever decode throughput cannot match backend rename and dispatch bandwidth.

B. The Role of the Micro-op Cache

To circumvent the frontend bottleneck, modern high-performance microarchitectures (Intel Sandy Bridge through Raptor Lake, AMD Zen 1 through Zen 4) incorporate an on-chip Micro-op (Uop) Cache. Positioned alongside the L1 instruction cache, the uop cache stores pre-decoded micro-ops. When a fetch Program Counter (PC) hits in the uop cache, the CPU clock-gates the L1 instruction cache, pre-decoders, and x86 decoders. Micro-ops stream directly into the rename stage at high bandwidth (up to 8 uops/cycle in Zen 3), substantially reducing branch misprediction penalty and frontend energy.

C. Variable Cost vs. Fixed-Size Caches

In traditional caches (L1D, L2, L3), every cache entry stores a fixed 64-byte block, and every hit yields identical benefit. Under these conditions, Belady's MIN algorithm (evicting the block whose next access is furthest in the future) is provably optimal.

In contrast, uop caches operate on Prediction Windows (PWs):

  1. Variable Cost ($c_i$): A Prediction Window delivers between 1 and $N$ micro-ops (e.g., 1 to 32 uops). A hit on a window delivering 16 uops provides far greater execution benefit and pipeline throughput than a hit on a single-uop window.
  2. Variable Footprint ($s_i$): Because each physical cache entry (way) accommodates up to $U$ micro-ops (e.g., $U = 8$), a window of $c_i$ uops occupies:
    $$s_i = \left\lceil \frac{c_i}{U} \right\rceil \text{ ways}$$(1)
    A small window occupies 1 way, while a larger window spans up to 4 ways in the set.
  3. Knapsack Equivalence: Evicting a single 4-way entry vacates space for four 1-way entries. Deciding whether to retain one high-cost large window versus multiple low-cost small windows transforms cache eviction into an online 0-1 Knapsack Problem, rendering conventional replacement policies (LRU, SRRIP) fundamentally sub-optimal.

II. Theoretical Formulation & Policies

A. Prediction Window Construction Semantics

In accordance with HPCA 2025 and AMD Zen 3 specifications:

  • A Prediction Window commences at: (1) the target address of a taken branch, or (2) the initial address of a 64-byte instruction cache line.
  • A Prediction Window terminates when: (1) a branch instruction is predicted taken, or (2) the sequential instruction stream crosses a 64-byte cache line boundary.
  • Microcode ROM Exclusion: Windows containing micro-ops originating from microcode ROM (e.g., sysenter, cpuid) are excluded from uop cache allocation and must be served via the legacy decode pipeline.

B. Belady MIN for Variable Footprint Caches

Belady's classical offline optimal algorithm selects the candidate whose next access occurs furthest in the future. In variable-footprint caches, Belady is implemented by tracking the exact future access timestamp for each window. When eviction is required, candidate ways are evaluated to find $\arg\max(t_{\text{next}})$. However, because Belady disregards variable footprints ($s_i$) and costs ($c_i$), it can evict high-density windows prematurely.

C. FLACK: Cost-Aware Greedy Knapsack Heuristic

Inspired by the greedy $\frac{1}{2}$-approximation algorithm for the fractional knapsack problem, FLACK defines the unit-cost $u_i$ of each Prediction Window as its micro-op density:

$$u_i = \frac{c_i}{s_i} = \frac{\text{Micro-op Cost}}{\text{Ways Occupied}}$$(2)

When set contention occurs:

  • Victim Selection: FLACK evicts the resident entry with the minimum unit cost:
    $$\text{Victim} = \arg\min_{w \in \text{Set}} u_w$$(3)
  • Dynamic Selective Bypassing: If an incoming window has a unit cost lower than the minimum unit cost currently resident in the set:
    $$u_{\text{new}} < \min_{w \in \text{Set}} u_w$$(4)
    the incoming window bypasses allocation entirely, protecting high-density resident entries from thrashing.

D. FURBYS: Frequency and Unit-Cost Replacement

While FLACK maximizes unit-cost density, it lacks temporal frequency awareness. Frequently executed windows with moderate unit costs can be repeatedly evicted by infrequently accessed windows with marginally higher unit costs. FURBYS resolves this deficiency through four integrated mechanisms:

+-------------------------------------------------------------+ | FURBYS REPLACEMENT PIPELINE | +-------------------------------------------------------------+ Incoming PW (weight W_new) | v [ 1. Selective Bypass Evaluator: W_new + K < min(W_set) ] |--- YES ---> [ BYPASS INSERTION ] | NO v [ 2. Min-Weight Selection with Hierarchical Tie-Breakers ] (min Weight --> max RRPV --> oldest LRU timestamp) | v Candidate Way V [ 3. 2-Slot Miss-Pitfall Detector: Is Way V in Pitfall FIFO? ] | +--- YES ---> [ Degrade to SRRIP ] (Clear Pitfall Buffer) | +--- NO ---> [ Evict Way V ] (Append V to Pitfall FIFO) +-------------------------------------------------------------+
Fig. 1. Architecture of the FURBYS Decision Engine.
  1. 3-bit Offline Profile Weights ($W_i \in \{0, \dots, 7\}$): Each Prediction Window is profiled offline under a trace-driven FLACK solver. Hit rates are partitioned per cache set using Fisher-Jenks Natural Breaks 1D clustering into 8 discrete groups. High-frequency, high-value windows receive $W = 7$, while rare windows receive $W = 0$.
  2. Min-Weight Selection with Hierarchical Tie-Breaking: The primary victim is the entry with the minimum weight:
    $$\text{Victim} = \arg\min_{w} W_w$$(5)
    If multiple entries share the minimum weight, FURBYS breaks ties using the entry with the maximum Re-Reference Prediction Value ($\max \text{RRPV} \in \{0, 1, 2, 3\}$). If RRPVs are equal, the Least Recently Used (oldest lastTouchTick) entry is evicted.
  3. Selective Bypassing ($K$-Threshold): Incoming windows whose weight is significantly below the set minimum bypass insertion:
    $$W_{\text{new}} + K < \min_{w \in \text{Set}} W_w$$(6)
    where $K \ge 0$ is a tunable parameter (default $K = 1$).
  4. 2-Slot Local Miss-Pitfall Detection & Fallback: To prevent set thrashing when offline profiles diverge from runtime phase behavior, each cache set maintains a 2-slot circular FIFO buffer of recently evicted way indices. If the min-weight candidate matches an index in the pitfall buffer (repeated eviction of the same slot), a miss pitfall is detected. FURBYS immediately degrades to standard SRRIP for that decision, evicts the cold entry, and clears the pitfall buffer.

III. Offline Profiling & Jenks Clustering

A. Profile Pipeline Architecture

To generate the 3-bit weights for FURBYS, our offline pipeline executes in three stages:

  1. Trace Generation: gem5 is executed with --uop-entries=0, logging every Prediction Window lookup, insertion, micro-op cost, and footprint to a structured execution trace file.
  2. FLACK Knapsack Replay: flack_offline_solver.py parses the trace and models set contention under greedy unit-cost eviction, computing individual hit rates:
    $$\text{HR}(\text{PC}) = \frac{\text{Hits}(\text{PC})}{\text{Accesses}(\text{PC})}$$(7)
  3. Fisher-Jenks Natural Breaks Clustering: jenks_natural_breaks.py groups hit rates per cache set into 8 natural break clusters.

B. Fisher-Jenks Optimization Formulation

The Fisher-Jenks algorithm partitions 1D continuous data into $k=8$ classes such that the Sum of Squared Deviations from the Class Mean (SDCM) is minimized while the Sum of Squared Deviations from the Grand Mean (SDAM) is maximized:

$$\text{SDCM} = \sum_{j=1}^k \sum_{i \in C_j} (x_i - \bar{x}_j)^2$$(8)

Using dynamic programming matrices $D[i, j]$ (variance of subrange $i \dots j$) and $M[i, c]$ (minimum variance partitioning $i$ items into $c$ classes), the algorithm achieves optimal variance fit:

$$\text{GVF} = 1 - \frac{\text{SDCM}}{\text{SDAM}}$$(9)

The resulting boundaries produce discrete 3-bit integers ($0 \le W \le 7$) written to furbys_weights.txt and ingested by gem5 at initialization.

IV. gem5 Implementation Architecture

A. Codebase Integration

The implementation is cleanly partitioned into modular C++ components in src/cpu/o3/:

  • uop_cache.hh / .cc: Implements CachedUop, PredictionWindow, AccumulationBuffer, and UopCache. Encapsulates replacement algorithms (LRU, SRRIP, Belady, FLACK, FURBYS), bypass evaluation, pitfall tracking, and profile file loaders.
  • fetch.hh / .cc: Integrates uop cache lookup, window serving, accumulation buffer management, and snooping into Fetch::fetch() and Fetch::IcachePort.
  • BaseO3CPU.py: Exposes Python SimObject parameters for cache size, associativity, replacement policy, switch delay, decode delay, and profile paths.
  • SConscript: Registers uop_cache.cc and the UopCache debug trace flag.

B. Strict Inclusiveness via L1 Snooping

The uop cache enforces strict inclusion with the L1 instruction cache. Fetch::IcachePort overrides recvTimingSnoopReq, recvFunctionalSnoop, and recvAtomicSnoop. Any cache line invalidation snooped from the memory subsystem triggers uopCache->invalidateByIcacheAddr(pkt->getAddr(), cacheBlkSize), evicting all Prediction Windows that originated from that physical block.

C. Frontend Pipeline Coordination

At each cycle in Fetch::fetch(), if atPWBoundary[tid] is true, the uop cache performs a tag lookup on this_pc.instAddr(). On a hit, uopCacheServing[tid] is asserted, legacy decoding is bypassed, and micro-ops are dispatched to the rename stage. On a miss from uop cache mode, a 1-cycle switch delay penalty is charged via uopCacheStallCycles[tid] before legacy instruction fetch resumes.

V. Critical Engineering Challenges

A. Snoop Request Panics at Tick 0

Symptom: gem5 aborted during initialization with panic: system.cpu.icache_port was not expecting a functional snoop request.

Root Cause: Declaring isSnooping() == true on IcachePort caused gem5's SE-mode binary loader (TranslatingPortProxy) to broadcast functional snoops during process setup, which IcachePort did not handle.

Fix: Implemented recvFunctionalSnoop and recvAtomicSnoop in fetch.hh and fetch.cc, safely routing invalidations to fetch->invalidateUopCache(...).

B. Decoder Desynchronization at Tick 906135

Symptom: LRU, SRRIP, Belady, and FURBYS crashed at tick 906135 with panic: Tried to read unmapped address 0. PC: (0x415b04=>0x415b06).(0=>1), Instr: SAL_M_R : ldst t1b, DS:[rcx].

Root Cause: When the uop cache finished serving a Prediction Window ending at PC 0x415b03, the legacy decoder state had not been cleared. pcOffset retained a residual value of 1 from prior decoding, causing the next I-cache fetch to read misaligned at 0x415b04. The true instruction was xor edx, edx (bytes 31 d2 at 0x415b03). Fetching from byte offset 1 caused the decoder to ingest byte d2 followed by 31, which x86 decodes as SAL_M_R : ldst t1b, DS:[rcx]. At commit, rcx == 0, triggering a page fault on unmapped address 0.

Fix: Enforced strict state hygiene: whenever entering uop cache mode, exiting uop cache mode, or handling a squash, decoder[tid]->reset(), fetchBufferValid[tid] = false, fetchOffset[tid] = 0, pcOffset = 0, and macroop[tid] = nullptr are reset.

C. Next-PC Double-Advancement Fix

Symptom: Instructions replayed from uop cache skipped alternate PC states.

Root Cause: Replay logic assigned set(next_pc, *uop.nextPC) and then called bac->updatePC(instruction, *next_pc, curFT), which called staticInst->advancePC(*next_pc) again on an already-advanced PC.

Fix: Replaced with set(next_pc, this_pc) before updatePC, ensuring bac->updatePC advances the PC exactly once, matching legacy fetch semantics.

D. Pipelined I-Cache Fetch Inhibition

Symptom: Redundant I-cache requests issued while uop cache was active.

Root Cause: issuePipelinedIfetch[tid] did not check uop cache status.

Fix: Added !uopCacheServing[tid] && !inUopCacheMode[tid] to inhibit pipelined I-cache accesses while running out of the uop cache.

VI. Experimental Results & Discussion

A. Hardware Configuration & Setup

The simulated CPU models an AMD Zen 3 core frontend at 3.2 GHz, 8-wide fetch, 4-wide decode, 6-wide rename/dispatch, 256-entry ROB, 96-entry RS, 32 KiB 8-way L1I (1-cycle latency), 32 KiB 8-way L1D (2-cycle latency), 512 KiB 8-way L2 (16-cycle latency), and DDR4-2400 DRAM.

B. Quantitative Discussion

1. Substantial Frontend Filtering: Enabling the uop cache dramatically reduces L1 instruction cache demand accesses. Under LRU, SRRIP, and FURBYS, L1 I-cache demand hits dropped from 1,886 down to 837–889 — a 55.6% reduction in L1 I-cache hits. Over 11,400–11,900 micro-ops were supplied directly from the uop cache, completely clock-gating the x86 decoders and reducing I-cache stall cycles from 11,861 down to 11,685 cycles.

2. Policy Comparison (LRU vs. SRRIP vs. FURBYS):

  • LRU achieved the highest window hit rate (67.53%) and micro-op hit rate (50.81%) on this compact benchmark due to strong short-term temporal recency in initialization loops.
  • SRRIP followed closely with a 66.32% window hit rate and 48.95% micro-op hit rate, demonstrating effective scan resistance using 2-bit RRPV states.
  • FURBYS achieved a 66.11% window hit rate and delivered 11,395 micro-ops. Crucially, the 2-slot miss-pitfall detector successfully caught 79 thrashing events, dynamically degrading eviction to SRRIP to clear cold entries, while 307 evictions were guided strictly by 3-bit offline weights. This confirms that FURBYS provides competitive hit rates while preventing phase-transition degradation.

3. FLACK Greedy Bypass Dynamics: FLACK registered 1,313 bypasses and a 19.03% hit rate. Because FLACK strictly enforces $u_{\text{new}} < \min u_{\text{set}}$, once early high-density windows fill a set, moderate-sized windows are aggressively bypassed. This validates the paper's finding that pure unit-cost greedy heuristics require multi-phase threshold moderation in tight loops.

4. Belady Offline Replay: Belady achieved a 61.10% window hit rate. Because Belady tracks scalar timestamps without accounting for multi-way footprint ($s_i$), evicting a multi-way window needed far in the future can still hurt performance if subsequent single-way windows do not compensate for the lost micro-op volume.

VIII. Conclusion

This project successfully implemented and evaluated the HPCA 2025 research paper in gem5 O3CPU. By treating uop cache eviction as a variable-footprint 0-1 Knapsack Problem, we modeled Prediction Window accumulation, 1-cycle switch delay penalties, and strict L1 I-cache snooping inclusiveness. We integrated five policies (LRU, SRRIP, Belady, FLACK, FURBYS) alongside a Fisher-Jenks 1D clustering suite. Our results demonstrate that uop caching filters over 55.6% of L1 I-cache demand queries and supplies over 50% of executed micro-ops directly to the pipeline, while FURBYS's miss-pitfall detector robustly adapts between offline weights and dynamic SRRIP fallback.
